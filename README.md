# Мой автомеханик — экосистема

Четыре приложения работают на одном сервере и видят одни и те же заказы в реальном времени:

| Приложение | Кто пользуется | Где работает | Папка |
|---|---|---|---|
| **Мой автомеханик** | клиентка | Android, iOS, веб | `apps/client`, `mobile/client` |
| **Консьерж** | водитель, который перегоняет машину | Android, iOS, веб | `apps/concierge`, `mobile/concierge` |
| **Панель СТО** | станция техобслуживания | веб | `apps/sto` |
| **Панель диспетчера** | диспетчер и директор | веб | `apps/dispatcher` |

Интерфейсы взяты из прототипов (клиентка v1.9, СТО v1.6, диспетчер, консьерж) без перерисовки. Выдуманных данных нет: система стартует пустой, клиентки, СТО и консьержи регистрируются сами, а всё, что видно в приложениях, создали реальные пользователи.

## Боевой сервер

Сервер развёрнут на Render: **https://moy-avtomekhanik.onrender.com**. Там же доступны веб-версии: `/client/`, `/concierge/`, `/sto/`, `/dispatcher/`. Мобильные приложения подключаются к нему по умолчанию.

Сервер на бесплатном плане: после 15 минут без запросов он засыпает, первое открытие занимает около минуты. Аккаунты и данные хранятся в Supabase и при перезапуске не теряются.

## Вход и регистрация (Supabase)

Аккаунты ведёт [Supabase Auth](https://supabase.com/docs/guides/auth): вход по email и паролю, подтверждение email, восстановление пароля.

| Кто | Как появляется аккаунт |
|---|---|
| Клиентка | регистрируется в приложении «Мой автомеханик» |
| СТО | регистрируется в панели СТО: название, адрес, контактное лицо |
| Консьерж | регистрируется в приложении консьержа |
| Диспетчер, директор | регистрируется в панели диспетчера, потом администратор выдаёт роль SQL-запросом из `supabase/schema.sql` |

Один аккаунт — одна роль: аккаунт клиентки не откроет панель СТО. Роль из регистрации не даёт доступа к диспетчерской, эту роль выдаёт только администратор (`app_metadata`).

Как это устроено: приложение получает токен в Supabase и передаёт его серверу. Сервер проверяет токен запросом в Supabase, узнаёт id пользователя и его роль, а при первом входе создаёт профиль из данных регистрации. Каждое действие проверяется на сервере: доступно ли оно этой роли и её ли это заказ.

### Настройка Supabase (один раз)

1. Создайте проект на https://supabase.com (бесплатный план подходит).
2. **SQL Editor** → вставьте `supabase/schema.sql` → **Run**. Появятся таблицы `app_state` и `events`.
3. **Authentication → URL Configuration**:
   - *Site URL*: адрес сервера, например `https://moy-avtomekhanik.onrender.com/client/`;
   - *Redirect URLs*: добавьте `https://moy-avtomekhanik.onrender.com/**` (и `http://localhost:8080/**` для разработки).
   Сюда ведут ссылки из писем: подтверждение email и новый пароль.
4. **Authentication → Emails**: встроенная почта Supabase отправляет всего несколько писем в час и годится только для проверки. Для реальных пользователей подключите свой SMTP (Resend, Brevo, Mailgun и т. п.) в *SMTP Settings*. Подтверждение email можно отключить в *Sign In / Providers → Email → Confirm email*, тогда вход сразу после регистрации.
5. **Project Settings → API Keys** — скопируйте три значения в переменные окружения сервера:

| Переменная | Где взять | Секретная? |
|---|---|---|
| `SUPABASE_URL` | Project URL, `https://xxxx.supabase.co` | нет |
| `SUPABASE_ANON_KEY` | publishable key (`sb_publishable_…`) или legacy `anon` | нет, уходит в приложения |
| `SUPABASE_SERVICE_KEY` | secret key (`sb_secret_…`) или legacy `service_role` | **да**, только на сервере |

Без `SUPABASE_SERVICE_KEY` сервер хранит данные в локальном SQLite (`DB_FILE`), вход всё равно идёт через Supabase.

### Назначить диспетчера

Человек регистрируется в `/dispatcher/`. Сервер не пустит его, пока у аккаунта нет роли. Затем в SQL Editor:

```sql
update auth.users set raw_app_meta_data = raw_app_meta_data || '{"role":"dispatcher"}'
where email = 'dispatcher@example.com';
```

Для директора укажите `"director"`. Роль начинает действовать примерно через минуту, после нового входа.

## Быстрый старт (разработка)

Нужен Node.js 22.5 или новее: используется встроенный SQLite.

```bash
cd server && npm install
SUPABASE_URL=https://xxxx.supabase.co SUPABASE_ANON_KEY=sb_publishable_… npm start
```

Без Supabase можно работать в режиме разработки, где вход идёт без пароля, по одному имени:

```bash
cd server && AUTH_DISABLED=1 npm start
```

Откройте http://localhost:8080/. Там страница экосистемы: все четыре приложения рядом и лента событий (её видно после входа в панели диспетчера). Каждое приложение можно открыть и отдельно: `/client/`, `/concierge/`, `/sto/`, `/dispatcher/`. **`AUTH_DISABLED=1` никогда не включайте на боевом сервере.**

Нажатие на индикатор связи в углу приложения открывает аккаунт: там видно, кто вошёл, и есть кнопки «Выйти» и «Сменить адрес сервера».

## Как заказ проходит через все приложения

```
Клиентка             СТО                    Консьерж                Диспетчер
─────────            ───                    ────────                ─────────
заявка ───────────▶ лента «Новые заявки»
                     предложение цены ───▶ (клиентке)
выбор СТО ─────────▶ «Мои заявки»   ──────▶ лента заказов ────────▶ «ждёт консьержа» / назначить
карта: консьерж едет ◀─────────────────────── шаги поездки, позиция
акт №1: подтвердить ◀──────────────────────── акт №1
                     акт №2: принять ◀─────── акт №2
статус «Диагностика» ◀ стадии
смета: одобрить ◀──── смета
                     «Готово» ────────────▶ заказ на возврат
                     акт №3 ──────────────▶ везёт клиентке
акт №4, оплата, оценка ◀───────────────────── акт №4
«Есть претензия» ─────────────────────────────────────────────────▶ спор → директор → возврат
SOS / эвакуатор ──────────────────────────────────────────────────▶ SOS 24/7
```

Чат по заказу общий: клиентка, мастер СТО, консьерж и диспетчер видят одну переписку. Уведомления приходят в каждое приложение. На телефоне, когда приложение свёрнуто, они показываются как системные.

## Архитектура

```
apps/                    веб-приложения (статические HTML/JS)
  shared/ma-sdk.js       общий SDK: вход и регистрация (Supabase Auth), WebSocket-синхронизация, действия, уведомления
  client/  client-sync.js        прототип v1.9 и слой синхронизации
  sto/     sto-sync.js
  dispatcher/ dispatcher-sync.js
  concierge/  concierge-app.js
  index.html             страница экосистемы
server/
  src/seed.js            справочники и пустое стартовое состояние
  src/domain.js          бизнес-логика: заказ, акты, споры, SOS; права на действия, профили, видимость данных
  src/auth.js            проверка токена Supabase, роль пользователя
  src/index.js           HTTP, REST, WebSocket, статика
  src/store.js           хранилище: Supabase Postgres или локальный SQLite
  test/                  тесты логики, входа и хранилища
supabase/schema.sql      таблицы и выдача ролей сотрудникам
mobile/
  client/, concierge/    проекты Capacitor 8 (android/, ios/)
  scripts/build-www.mjs  собирает веб-часть приложения из apps/ в www/
```

- **Протокол.** Приложение отправляет `hello {role, token}` с токеном Supabase и получает `state`: представление данных для своей роли. Действие уходит как `act {type, p}`, после него всем рассылается новое `state` и адресные `notify`. Позиция консьержа в поездке идёт отдельными лёгкими сообщениями `loc`.
- **Приватность.** СТО видит телефон и адрес клиентки только после того, как клиентка выбрала эту станцию. Консьерж видит их только после того, как взял заказ. Это проверяется на сервере, в `viewFor`.
- **Права.** Таблица `PERMS` в `domain.js`: какие действия доступны каждой роли. Клиентка работает только со своими заказами, СТО — с заказами, где выбрали её (и предлагает цену на открытые заявки), консьерж — со своими поездками.
- **REST** для интеграций, с заголовком `Authorization: Bearer <токен>`: `GET /api/state?role=`, `POST /api/act`, `GET /api/events` (только сотрудники). Без токена: `GET /api/config`, `GET /api/health`.

## Развёртывание сервера (чтобы приложения работали с телефона)

Телефону нужен сервер, доступный из интернета по **HTTPS**. Есть два способа.

### Вариант А. Render.com: бесплатно, без своего сервера

1. Зарегистрируйтесь на https://render.com через GitHub.
2. Откройте Dashboard → **New → Blueprint**, выберите репозиторий `Tapashka/ServiceMan` и ветку `main` (или ветку из пул-реквеста). Render прочитает `render.yaml` и соберёт `Dockerfile`.
3. Render спросит `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_KEY` — вставьте значения из Supabase (см. «Настройка Supabase»). У уже созданного сервиса их добавляют в Environment.
4. Через 3–5 минут появится адрес вида `https://moy-avtomekhanik.onrender.com`. Откройте его в браузере телефона: должна открыться страница экосистемы.

На бесплатном плане сервис засыпает после 15 минут без запросов, и первое открытие занимает около минуты. Данные хранятся в Supabase и при перезапуске не теряются.

### Вариант Б. Свой сервер (VPS) с Docker

Подойдёт любой VPS с Ubuntu и 1 ГБ памяти, плюс домен.

```bash
# DNS: A-запись ma.ваш-домен.by → IP сервера
git clone https://github.com/Tapashka/ServiceMan.git && cd ServiceMan/deploy
printf 'SUPABASE_URL=…\nSUPABASE_ANON_KEY=…\nSUPABASE_SERVICE_KEY=…\n' > .env
DOMAIN=ma.ваш-домен.by docker compose up -d --build
```

Caddy сам выпустит сертификат Let's Encrypt. Данные хранятся в Supabase, а без `SUPABASE_SERVICE_KEY` — в томе `ma-data`.

### Автодеплой с GitHub

Каждый push в `main` прогоняет тесты сервера. Если тесты прошли, GitHub Actions запускает деплой на Render (задача «Деплой сервера на Render»). Чтобы это работало, один раз сделайте так:

1. Render → сервис `moy-avtomekhanik` → **Settings** → **Deploy Hook** → скопируйте URL.
2. GitHub → репозиторий → **Settings → Secrets and variables → Actions → New repository secret**: имя `RENDER_DEPLOY_HOOK`, значение — скопированный URL.

URL хука — секрет: с ним кто угодно может запустить деплой. Если он утёк, перевыпустите его в Render (Regenerate).

Пока секрет не задан, задача деплоя пропускается с предупреждением, остальная сборка не падает.

### Подключить мобильные приложения к серверу

1. GitHub → Settings → Secrets and variables → Actions → вкладка **Variables** → New variable: `MA_SERVER_URL` = `https://ваш-адрес`.
2. Actions → «Сборка экосистемы» → **Run workflow**. Адрес можно указать и прямо в поле запуска.
3. Скачайте APK из Artifacts и установите на Android: в настройках телефона разрешите установку из этого источника.
4. Приложение, которое уже установлено, можно не пересобирать: нажмите на индикатор связи вверху экрана и введите адрес сервера.

На iPhone приложение без аккаунта Apple Developer не установить. До его появления откройте `https://ваш-адрес/client/` в Safari и выберите «Поделиться → На экран „Домой“».

## Мобильные приложения (Android и iOS)

```bash
cd mobile && npm install
MA_SERVER_URL=https://ваш-сервер npm run sync    # веб-часть из apps/ → www → нативные проекты
npm run open:client:android                      # Android Studio
npm run open:client:ios                          # Xcode (на Mac)
```

- По умолчанию приложения подключаются к `https://moy-avtomekhanik.onrender.com`. Для локального сервера соберите с `MA_SERVER_URL=local`: Android-эмулятор → `http://10.0.2.2:8080`, iOS-симулятор → `http://localhost:8080`. Адрес можно сменить прямо в приложении: нажмите на индикатор связи вверху экрана.
- Для HTTP-сервера в демо разрешён незашифрованный трафик (`usesCleartextTraffic`, `NSAllowsArbitraryLoads`). Для публикации в магазины нужен HTTPS, а эти исключения надо убрать.
- Разрешения: геопозиция (маршрут до СТО у клиентки, трансляция поездки у консьержа), уведомления, камера (акты у консьержа).
- Идентификаторы: `by.moyavtomekhanik.app` и `by.moyavtomekhanik.concierge`. Иконки и заставки лежат в `mobile/*/assets`, перегенерировать их можно командой `npx @capacitor/assets generate`.

### CI-сборки

Workflow `.github/workflows/build.yml` на каждый push:

- запускает тесты сервера;
- собирает **Android APK** (debug) для обоих приложений;
- собирает **iOS** для симулятора и неподписанный `.ipa` для устройства, на macOS-раннере.

Готовые файлы скачиваются в Actions → Artifacts. Адрес сервера задаётся переменной репозитория `MA_SERVER_URL` или полем при ручном запуске.

### Что нужно для публикации в Google Play и App Store

1. Развернуть сервер с HTTPS (см. раздел «Развёртывание сервера»).
2. Android: ключ подписи (keystore), сборка `./gradlew bundleRelease`, аккаунт Google Play Console.
3. iOS: аккаунт Apple Developer, сертификат и provisioning profile, архив через Xcode или `xcodebuild archive`.
4. Push-уведомления в фоне через FCM и APNs. Сейчас уведомления приходят, пока приложение открыто или свёрнуто, но живо. Закрытое приложение их не получит.
5. Оплата: привязка карты и списание через платёжного провайдера (bePaid, Assist, WebPay и т. п.). Номера карт нельзя хранить ни в приложении, ни на своём сервере. Сейчас оплата и смена пакета отмечаются без реального списания.
6. Вход по телефону и SMS, если он нужен: Supabase поддерживает его через Twilio, MessageBird или Vonage.
